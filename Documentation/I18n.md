# Internationalization (i18n)

This document describes widget-level internationalization in the CMS: how supported languages are configured, how localized widget config is stored and edited, and how the viewer selects and passes the active language to widgets.

## Overview

- **Scope:** Widget-level i18n only. There is no full app/route-level i18n (e.g. locale in URL path or translated builder UI).
- **Per-brand languages:** Each brand’s Site Settings define which languages are supported. The builder uses this list to show one input per locale for localized fields.
- **Published pages:** The viewer chooses language from the `?lang=` query parameter. That value is validated against the site’s supported languages and passed to all widget renderers.
- **Config shape:** A localized config value can be a **string** (legacy, single language) or a **`Record<lang, string>`** (e.g. `{ "en-GB": "Hello", "fr-FR": "Bonjour" }`). Widgets resolve the display value using a small helper that supports both. Locale codes use the 5-character language-region form (e.g. en-GB, fr-FR).

## Site Settings

Supported languages are configured per brand in the **Site Settings** dialog (builder).

- **Storage:** Backend stores them as `SupportedLangsJson` on the `SiteSettings` entity (JSON array, e.g. `["en-GB","fr-FR"]`). Frontend exposes this as `siteSettings.supportedLangs`. Each entry must be a 5-character locale code (language-region, e.g. en-GB, fr-FR).
- **Builder:** The Properties Panel uses this list to decide which locales to show for every `localizedText` field (tabs, stacked inputs, or dropdown). If Site Settings has no languages set, the panel falls back to the field’s `langs` schema attribute, then to the default locale (e.g. en-GB).

## Widget schema: localizedText

For any config field that should have one value per language:

- **Type:** `localizedText`
- **Optional:** `langs` — array of locale codes (e.g. `["en-GB","fr-FR"]`) used when the site has no supported languages configured. If the site has `supportedLangs`, that list is used instead.
- **Stored value:** Either a string (legacy) or an object `{ [lang]: string }`, e.g. `{ "en-GB": "Submit", "fr-FR": "Envoyer" }`.
- **Fallback order for which locales appear in the builder:** `siteSettings.supportedLangs` → `field.langs` → default locale (e.g. en-GB).

Example (C#):

```csharp
new { name = "buttonText", label = "Button Text", type = "localizedText", required = true, langs = new[] { "en-GB", "fr-FR" } }
```

Default config for that field can be a string or an object, e.g. `{ "en-GB": "Submit", "fr-FR": "Envoyer" }`.

## Builder

- **Source of locales:** `supportedLangs` comes from PageBuilderContext, which reads it from the current brand’s Site Settings.
- **How localized fields are shown:** The Properties Panel can show localized fields as **tabbed** (one tab per locale), **stacked** (one label + input per locale), or **dropdown** (select locale then one input). The preference is stored in localStorage (`cms.localizedTextView`).

## Viewer (published pages)

- **How `lang` is chosen:** The preview/published page reads `?lang=xx` from the URL. If `xx` is in the site’s `supportedLangs`, that is used; otherwise the first supported language is used, or the default locale (e.g. en-GB) if none are set.
- **Flow:** Preview page → `SiteLayoutWrapper` (receives `lang`) → `PublishedPageRenderer` / `StandaloneWidgetRenderer` → each CustomRenderer receives a `lang` prop. Renderers should use this when resolving localized config values.

**HTML embed:** The external fragment endpoint `GET /api/embed/widget` accepts an optional `lang` query parameter so inlined HTML matches the requested locale. See [widget-html-embed.md](./widget-html-embed.md).

## Implementing a widget

1. **Schema:** For any user-facing text that should vary by language, use `type: "localizedText"` and optionally `langs` in the field definition.
2. **Renderer:** Your CustomRenderer receives an optional `lang` prop (defaults to the default locale, e.g. en-GB, when not provided). For every localized config property, use `getLocalizedValue(config.fieldName, lang)` from `@/lib/i18nWidgetConfig`. It handles both legacy string values and `Record<lang, string>` and returns a single string (with fallback: requested lang → language part, e.g. en from en-GB → first non-empty value).
3. **Default config:** For `localizedText` fields, defaultConfig can be a string or an object keyed by language.

Example (React):

```tsx
import { getLocalizedValue, DEFAULT_LANG } from '@/lib/i18nWidgetConfig';

const MyRenderer: CustomRenderer = ({ config, lang = DEFAULT_LANG }) => (
  <button>{getLocalizedValue(config.buttonText, lang) || 'Submit'}</button>
);
```

| Layer   | File | Purpose |
|--------|------|---------|
| Frontend | `frontend/lib/i18nWidgetConfig.ts` | `DEFAULT_LANG`, `isLocalizedValue`, `getLocalizedValue` |
